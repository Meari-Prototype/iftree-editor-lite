# 概念与设计

> [上手教程](getting-started.md) · [操作指南](how-to.md) · [参考手册](reference.md) · **概念与设计**

解释这个工具为什么长这样。不教操作（那是[操作指南](how-to.md)的事），只讲设计与取舍。

## 要解决的问题

面向规模较大的多文档语料（设计目标为百亿字级），核心诉求是两个：

1. **找得准**：在海量原文中定位到具体几句，而不是「这篇文档里大概有」。
2. **信得过**：结果能回溯到原文出处，不被模型臆测替代。

后面所有设计都从这两条推出来。

## 条件树与稳定地址

把原文整理成树，每个节点有形如 `1-3-2` 的地址。地址不是存死的编号，而是由 `parent_id + sort_order` 动态生成。于是每个句子都有一个**可引用的坐标**：检索结果、agent 回答、节点间引用、历史 diff 都用地址说话，人能照着地址核对。

节点级粒度是刻意的：导入时就切到句子级，粒度在导入期锁定。检索命中是「第几个节点」而不是「第几页」，代价是导入前要把结构定好——这笔交易换来的是引用永远精确。

## 双密度阅读

同一份内容在两种密度间切换：折叠时是 Markdown 文档，展开时是可操作的条件树。两种视图共享同一份原文——导入时保留句子到原文的 offset 映射，存的是映射不是拷贝。原文本身（`source_documents` / `source_spans`）只记 offset，不重组正文结构，所以任何视图都能溯回到源文的字节位置。

## 证据纪律

内置 agent 回答事实问题时，必须先读取正文证据并给出证据节点地址，不以模型常识或题目措辞作答。检索命中只用于挑候选；回答前用 `read` 取回正文。这条纪律同样写进了 MCP 工具的 description，期望外部 agent 遵守同一动线：`find` 挑候选 → `read` 取证据 → 回答附地址。

## 信任分级

节点分两级：**受控**与**不受控**。受控 = 经人工审批的结论；不受控 = 机器产物未经人审。这是「是否过了人这一关」的时态属性，不是质量评分——智能导入、agent 写入的产物一律不受控，不存在「写得好就升级」的通道，升级的唯一方式是人审。

ERROR 是一类特殊节点：命中未解决的 ERROR 时，agent 必须停下向用户报告，不得绕过续跑。

## 编辑模型：唯一草稿与快进提交

Lite 把编辑边界压得很窄：节点正文和树结构不可编辑；一份已导入文档只允许修改节点备注、节点类型、引用与实体关系。稳定节点 id 用于记录这些动作，地址仍只负责给人定位。

每篇文档最多有一份活跃草稿。`draft` 幂等开稿，`edit` 逐条记录动作，`undo` / `redo` 只在草稿内移动 active 边界；`commit` 把 active entries 重放到正文、创建历史并销稿，`discard` 丢弃草稿。

产品不提供 `merge`、`rebase`、`cherry-pick` 或冲突裁决器，也不允许通过草稿修改正文、插入 / 删除 / 移动节点。若需要改变文档结构，应修正源文件后重新导入，而不是在库内重塑原文。

## 共享后端

SQLite 是单写者数据库，而这里至少有三类客户端：应用、MCP server、命令行脚本。解法是**一库一后端**：数据库由一个 headless 后端进程独占，所有客户端连它。先到的客户端拉起后端；后来者按数据库绝对路径哈希派生的命名管道接入（描述文件放数据库同目录，丢失也能在同一管道名会合）。于是应用开着的同时，外部 agent 可以通过 MCP 操作同一个库，互不踩踏。

## 本地优先

文档、结构、向量、历史与 Agent 会话全部在本地（SQLite + LanceDB）。默认语义向量由本机 Ollama 运行 Qwen3 Embedding 0.6B；模型下载完成后，嵌入和检索不依赖云服务。需要网络的可选环节是调用外部 LLM（摘要 / agent / 智能导入）与下载模型。MCP 是外部 agent 的数据边界，权限档在启动时锁定。
